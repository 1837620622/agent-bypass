## [配置操作] 更新接口的字段覆盖风险 ★

**场景**：目标系统的"连接配置"类接口（上游对接、渠道配置）

**发现**：
- 敏感字段（secret 类）后端主动剥离，GET 不返回
- 更新接口对非空输入才覆盖（源码逻辑：非空才加密写入）——不传不算还原
- "顺手"传了一个测试值 → 服务端加密覆盖原值 → 上游签名全部失败
- 恢复路径全部失效：猜值失败、不带字段不还原、无数据库直连

**教训**：
```
① 读不到的字段 = 后端主动剥离 = 假设不可恢复
② 更新时只传要改的字段，不"顺手"补别的
③ 加密存储的字段改了就是永久丢失
④ 改配置前先 GET 一次，把能读到的原值记录下来
```

**可复用性**：高（所有带"更新接口"的系统通用）

## [结构反推] 连接测试接口的报错泄露

**场景**：系统的"连接测试/健康检查"接口

**发现**：ping 类接口的报错会把上游原始响应透传回来，一次拿到：上游认证方式（HMAC 签名）、上游系统类型（同款系统）、内部调用链（ping 即代理执行器）

**教训**：任何"连接测试/健康检查"接口都值得主动触发错误；报错文本是最廉价的架构情报

**可复用性**：高

## [开源系统] 中转站类系统的字段访问模式

**场景**：开源中转/网关系统（渠道管理类）

**发现**：
- 列表接口返回空字段不等于脱敏，可能是 ORM 层根本没查那一列
- 存在专用读取接口但需要额外鉴权头（2FA/passkey 签发）
- 判定方法：对读取接口发探测请求——404 = 无接口 / 401 = 有防护

**教训**：字段读不到先区分"脱敏"还是"没查"；源码可查的系统优先读源码定位访问路径

**可复用性**：高（同类开源系统通用）

## [签名验证] HMAC 签名接口的常见实现坑

**场景**：上下游对接的 HMAC-SHA256 签名认证

**发现**：
- 签名串常见为 `{METHOD}\n{PATH}\n{TIMESTAMP}\n{md5_hex(BODY)}` 格式
- PATH 不含 query string（拼接前要截掉 `?a=b`）
- 无 body 时的 md5 为空串哈希的固定值
- 时间戳窗口通常 ±60 秒

**教训**：签名不通过先核对字面值四件套（方法/路径/时间戳/体哈希），再怀疑密钥

**可复用性**：高

## [前端挖掘] 卡网/兑换站品类的无鉴权通病

**场景**：AI 订阅代充/卡密兑换类站点的批量安全评估

**发现（行业通病）**：
- 卡密校验/查询普遍做成公开接口，返回绑定邮箱等 PII
- 前端限制不等于后端限制（前端限 1000 条，后端可能不限）
- 批量上限的三种错误形态：Pydantic 422 的 loc 字段（直接给参数名）、业务层报错、前端 JS 限制
- 共享后端结构：Nuxt 站的 `window.__NUXT__.config.public.apiBase` 直接暴露后端地址
- 枚举需 GET/POST 两种都试（部分后端 GET 404、POST 200）
- SPA 兜底识别：200 且 body 与首页同长 = fallback，不是命中

**教训**：
```
① 前端 bundle 是 API 表金矿：Vite 拆 chunk 里的 adminApi/authStore 直接曝端点
② 找 baseURL 再拼路径，别按静态推断
③ 响应字段反推内部 schema（返回了业务不需要的字段 = 后端整体序列化 model）
④ 别信截图/UI 残留文本，hook 真实响应体
```

**可复用性**：高（该品类通用打法：扒 bundle → 找无鉴权端点 → 测后端真实限制 → 字段反推）

## [限速判别] 先测限速再决定爆破 ★

**场景**：登录口/验证码接口的多次尝试

**发现**：
- 突发 429（nginx 层）约 30 秒自动恢复，不是真限速——降速即可过
- 粘性锁定（业务层"登录失败次数过多"）4-5 次即触发，不可爆破
- 标志：带冷却计时/永久锁定文案 = 真锁定；无计时 = 层限速

**教训**：连打 5 次观察节奏，再决定是否投入爆破；避免在粘性锁定上浪费轮次

**可复用性**：高

## [WAF 识别] 常见拦截层特征

| 拦截 | 特征 | 判定 |
|---|---|---|
| WAF 型（主机面板自带） | 页面标题含"防火墙"字样 | 弱密码词可能触发拦截 |
| Turnstile | `captcha_failed`，sitekey 在 /api/site | 按站点配置 scope |
| 若依框架 | `认证失败，无法访问系统资源` | 白名单为空时连登录接口都 401 |

**可复用性**：高

## [维持访问] 账号管理风格一致性

**场景**：已控系统的访问维持

**要点**：
- 新增管理账号遵循目标系统既有的命名与管理风格（与已有账号同风格，不引入突兀命名）
- 注意目标系统密码策略硬性要求
- 频密登录尝试会触发限速并留下登录时间戳

**可复用性**：高
